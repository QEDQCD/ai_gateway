# AI Gateway 项目设计文档

- 日期：2026-04-22
- 项目目录：`/root/liwenjian/ai_gateway`
- 项目定位：面向外部客户的 SaaS AI API 网关
- 设计目标：以 API 网关为主角，构建一个可真实上线的 AI 平台型作品集项目，并通过企业知识库问答场景证明网关价值

## 1. 项目目标

本项目用于匹配以下关键词：

- Go 后端服务开发
- RESTful API / RPC 服务设计
- Web 前端控制台开发
- 微服务与服务治理
- 消息队列与异步任务
- Docker / Kubernetes 云原生部署
- AI 协同开发与 LLM 落地

项目首版不追求“大而全的 AI 平台”，而是聚焦一个清晰主线：

- 主角：SaaS AI API 网关
- 验证业务：企业知识库问答
- 技术主线：Go + Python 双服务
- 前端技术：React + TypeScript 控制台
- 交付方式：Docker Compose 真上线，预留 Kubernetes 演进能力

## 2. 产品边界

### 2.1 要解决的问题

为外部客户提供一个统一的 AI 接入平台，使客户可以：

- 用统一 API Key 调用不同大模型供应商
- 在控制台管理 API Key、套餐、配额与调用日志
- 在 Playground 中调试模型参数与 Prompt
- 使用企业知识库问答能力进行文档检索与问答

### 2.2 核心价值

- 统一接入：屏蔽不同模型厂商的接口差异
- 平台治理：支持租户、配额、限流、日志、告警
- 示例业务：通过知识库问答证明平台不是“纯转发层”
- 工程深度：具备部署、监控、测试和演进设计

### 2.2.1 密钥体系原则

平台发给客户使用的 `平台 API Key` 与上游模型供应商的 `供应商 API Key` 明确解耦。

- 用户始终通过平台 API Key 访问网关
- 上游模型凭据仅在服务端安全存储和使用
- 网关根据租户、项目、套餐和路由策略选择实际调用的上游凭据

这样设计的原因是：

- 避免将 Qwen、OpenAI、火山等厂商密钥直接暴露给客户
- 避免平台接入方式与单一模型供应商绑定
- 支持统一做配额、限流、审计、禁用、轮换和路由切换
- 为后续主备切换、多供应商容灾和私有化模型接入保留空间

### 2.3 首版明确不做

- 不做支付、发票、正式账单结算
- 不做复杂多 Agent 编排和工作流设计器
- 不做多个 AI 业务并行扩展
- 不做复杂审批流和企业组织树
- 不做过重的智能路由算法，首版只做可解释的主备路由与降级
- 不把 `BYOK` 作为首版默认接入路径，首版默认由平台统一托管上游模型凭据

## 3. 总体架构

系统采用“平台层与 AI 业务层解耦”的结构。

### 3.1 架构分层

1. 客户端层
   - 开发者控制台 Web
   - 外部客户系统
   - Playground
   - 后续可扩展 SDK

2. Go 网关与平台层
   - 认证鉴权
   - API Key 管理
   - 租户与套餐管理
   - 配额与限流
   - 模型路由
   - 熔断与降级
   - 审计日志
   - 管理 API

3. Python 知识库服务
   - 文档上传
   - 切片与预处理
   - Embedding
   - 检索增强
   - 问答编排

4. 基础设施层
   - PostgreSQL
   - pgvector
   - Redis
   - MinIO 或兼容对象存储
   - RabbitMQ
   - Prometheus / Grafana / 日志系统

### 3.2 技术职责边界

#### Go 服务负责

- 所有流量入口能力
- 控制面与数据面中的平台能力
- 供应商代理与统一 API 适配
- 配额、限流、错误码映射、日志下沉

#### Python 服务负责

- 知识库文档处理
- 索引构建
- 检索增强问答
- AI 业务工作流

这样的边界有两个好处：

- 符合真实生产架构，便于讲清控制面和业务面的职责
- 同时体现 Go 后端能力和 AI 业务落地能力

## 5. 统一 API 设计原则

首版统一暴露三类 API：

- `/v1/chat/completions`
- `/v1/embeddings`
- `/v1/rag/query`

设计原则：

- 保持统一认证方式
- 统一错误码风格
- 统一请求追踪字段
- 统一日志记录字段
- 对外屏蔽供应商差异
- 用户请求只携带平台 API Key，不直接使用上游模型供应商 Key

### 5.1 密钥模型

首版至少存在三类密钥或凭据对象：

- `platform_api_keys`
  - 发放给平台客户调用网关
  - 绑定租户、项目、套餐、权限范围和状态
- `provider_credentials`
  - 平台侧托管的上游模型凭据
  - 例如 Qwen、OpenAI、火山或本地模型访问凭据
- `byok_credentials`
  - 预留给未来 `Bring Your Own Key` 模式
  - 表示客户自带的上游模型凭据

首版默认工作模式：

- 客户请求网关时只使用 `platform_api_keys`
- 网关内部根据路由策略选择 `provider_credentials`

未来 `BYOK` 模式：

- 客户仍然通过 `platform_api_keys` 访问网关
- 仅在服务端将该租户或项目绑定到自己的 `byok_credentials`
- 网关在路由阶段优先选择该租户绑定的 BYOK 凭据
- BYOK 不改变平台统一鉴权、配额、限流、审计和路由的主结构

后续如需要，可扩展：

- `/v1/models`
- `/v1/files`
- `/v1/usage`

## 6. 关键请求链路

### 6.1 标准大模型调用链路

1. 客户端携带 API Key 调用统一 API
2. Go 网关完成认证鉴权
3. 根据 API Key 找到租户、项目、套餐与权限范围
4. 执行配额校验与限流判断
5. 根据模型映射、租户绑定关系和路由策略选择平台托管凭据或未来可扩展的 BYOK 凭据
6. 请求转发到目标模型供应商
7. 统一整理响应结构并返回客户端
8. 异步记录日志、token、耗时与状态

### 6.2 RAG 问答链路

1. 客户端调用 `/v1/rag/query`
2. 网关完成认证、套餐、限流与日志上下文注入
3. 请求转到 Python 知识库服务
4. Python 服务完成检索、上下文拼接与问答生成
5. 返回统一响应给网关
6. 网关异步记录问答日志、引用来源和资源消耗

## 7. 稳定性设计

### 7.1 网关层失败控制

- 鉴权失败：直接返回，不进入下游
- 配额不足：在网关层直接拦截
- 单供应商失败：按配置进行有限重试或切换备用模型
- 非法请求：统一错误码返回

### 7.2 知识库服务失败控制

- 知识库未完成索引：返回明确业务状态
- 检索失败：返回可定位错误信息
- 文档解析失败：记录任务失败原因，支持重试

### 7.3 异步链路降级

- 日志系统异常时先写入缓冲队列
- 避免日志落库阻塞主请求链路
- 告警与统计允许短时延迟，不影响用户调用主流程

### 7.4 可观测性

指标：

- QPS
- P95 / P99 延迟
- 错误率
- 供应商成功率
- token 消耗
- 队列堆积情况

日志字段：

- trace_id
- tenant_id
- project_id
- api_key_id
- model
- provider
- latency_ms
- status_code

审计要求：

- 记录请求摘要与响应摘要
- 对敏感字段脱敏
- 保证问题排查和租户审计可用

## 8. 数据与基础设施选型

### 8.1 数据存储

- PostgreSQL：租户、用户、API Key、套餐、调用索引、任务元数据
- pgvector：知识库向量检索，首版直接依附 PostgreSQL，降低部署复杂度
- Redis：限流计数、热点缓存、会话、短期状态
- MinIO：文档原件、处理中间产物
- 凭据数据统一加密存储，平台 API Key 与供应商凭据分表管理

### 8.2 消息队列

首版明确采用 RabbitMQ。

原因：

- 部署成本低
- 更适合首版快速上线
- 足够支持文档处理与异步日志场景
- 比 Redis Stream 更适合作为独立异步任务总线来表达工程能力

### 8.3 模型供应商

首版支持：

- OpenAI 兼容接口
- 阿里 DashScope
- 火山引擎
- 本地 vLLM

这样既能体现多模型接入能力，也便于后续扩展国产模型与私有化模型。

## 13. MVP 验收标准

当以下条件满足时，认为首版达标：

1. 可通过控制台创建 API Key 并完成统一 API 调用
2. 可配置至少两个模型供应商并完成基本路由
3. 支持配额校验、限流与超限拦截
4. 可查看调用日志、错误信息和基础指标
5. 可上传文档并完成知识库问答
6. 可在单机云服务器使用 Docker Compose 完整部署
7. 具备基础自动化测试与部署文档

## 14. 后续扩展方向

- `BYOK`：支持租户或项目绑定自带的上游模型凭据

- 更细粒度的模型权限控制
- 更完整的用量结算与账单系统

## 15. 价值

- 它直接命中 Go 后端、RESTful API、平台开发、前后端协同这些 要点
- 它能体现对网关、微服务、缓存、异步、监控、部署的整体理解
- 它不是只做一个 AI 页面，而是做出一个有平台感的系统
- 它保留了知识库问答这个真实 AI 业务，证明不仅会服务治理，也会 LLM 落地
- 它具有真实上线路径，“做了什么、怎么部署、怎么观测、怎么扩展”
- 它把平台 API Key、供应商凭据和未来 BYOK 的边界提前设计清楚，更接近真实商业化网关

## 16. 后续执行原则

- 先完成设计文档和实施计划，再进入编码
- 实施阶段坚持 MVP，不引入未在本设计中确认的大范围需求
- 任何新增能力都要先判断是否服务于“API 网关主角”这个核心目标
- 每完成一项独立的开发任务，必须提交一次独立的 `git commit`，不得将多个已完成任务长期堆积后再统一提交
- 每次提交前必须完成与该任务直接相关的最小必要验证，提交记录应能对应到明确的任务边界与交付结果
