# 企业内部 AI 网关治理、账单与用户级监控分期设计

## 1. 设计结论

本设计将当前 AI Gateway 的后续能力划分为三个层次：

1. **一期：部门级治理**
   - 审批时配置租户自然月金额上限，默认 `10000￥`
   - 管理后台新增按租户生成账单的能力，并展示租户关联供应商
   - 对用户输入做基础校验、敏感信息脱敏和日志入库前防泄露处理

2. **二期：用户级调用与监控**
   - 支持企业内部“员工维度”的调用归因与监控
   - 用户维度确定为 **员工工号**
   - 提供用户级调用观测、费用统计、限流和审计能力

3. **TODO / 后续阶段**
   - 多 key 轮询与负载均衡
   - 自动熔断与错误率降级
   - TTFT 超时切换备用模型
   - 语义缓存
   - MCP 协议接入评估

本期不实现：

- 用户级限流
- `employee_no` 字段
- 自动熔断与 24h 不可用
- TTFT 超时切备用模型

原因不是这些能力没有价值，而是当前代码基础虽然已具备部分可复用能力，但若强行把治理、账单、用户级身份、主备切换一起做，会让本期范围失控。

## 2. 当前系统能力与约束

### 2.1 已有的核心维度

当前系统已经稳定存在以下维度：

- `tenant_id`：表示租户，在企业内部场景中可映射为“部门”
- `platform_api_key_id`：表示接入网关的应用或系统凭证
- `user_id`：当前仅能稳定表示“平台 API Key 归属用户”或“平台内部用户”，并不等于真实业务终端用户
- `console_user`：表示登录控制台执行审批、创建、查看等管理动作的后台用户

### 2.2 当前已经具备的基础能力

当前代码中已经存在以下可复用基础：

1. **租户级治理基础**
   - `tenant_id` 已贯穿认证、日志、聚合、控制台展示链路
   - 已存在租户额度策略、租户周期用量统计结构

2. **费用账本基础**
   - 已有模型单价快照和费用计算逻辑
   - 已有 `llm_request_logs.total_cost_microyuan`
   - 已有 `tenant_usage_ledger.total_cost_microyuan`

3. **供应商归因基础**
   - 每次调用都记录 `provider_credential_id`
   - 管理后台已存在 Provider / Model / Healthcheck 相关数据面

4. **观测基础**
   - 已有调用观测、失败明细、趋势聚合、首 Token 延迟等数据结构
   - 已有健康检查任务与健康状态存储

### 2.3 当前尚不具备的能力

当前代码尚未形成以下闭环：

- 基于金额的租户月度拦截
- 租户账单页及供应商维度账单展示
- 请求前内容安全与敏感数据脱敏闭环
- 用户级身份归因
- 用户级限流与监控
- 错误率熔断与自动恢复
- TTFT 超时切主备

## 3. 企业内部场景下的主体模型

### 3.1 一期主体模型

一期按照“部门级治理”建模：

- `tenant_id` = 部门
- `platform_api_key_id` = 部门下某个应用/系统的接入凭证
- `console_user` = 平台管理员或部门成员（用于后台管理，不用于业务调用归因）

这个模型足以支撑：

- 部门月度费用上限
- 部门账单
- 部门维度供应商成本分析
- 部门级审计与治理

### 3.2 二期主体模型

二期在以上基础上再补“员工维度”：

- `tenant_id` = 部门
- `platform_api_key_id` = 部门应用/系统接入凭证
- `employee_no` = 员工工号，表示真实业务调用人
- `console_user` = 后台管理操作人

这样可以把“谁的系统在调”和“哪个员工在使用”区分开，避免把同一个平台 API Key 下的所有调用都错误地归因到同一个归属用户。

## 4. 一期设计范围

## 4.1 审批增加租户自然月金额上限

### 4.1.1 目标

在 admin 审批通过账号申请时，除现有：

- 租户 ID
- Token 上限
- 可使用模型范围

之外，再增加：

- **月度金额上限**，默认值为 `10000￥`

金额上限的统计口径为：

- **自然月**
- 维度为：`tenant_id`
- 以累计 `total_cost_microyuan` 为准

### 4.1.2 行为规则

1. 审批通过时写入租户治理策略
2. 每次请求进入网关后，在路由与上游调用前，校验该租户当月累计费用
3. 如果当月费用已达到或超过上限，则直接拦截
4. 拦截错误统一按“额度超限”处理，但文案需要区分“Token 超限”和“金额超限”
5. 金额上限为 `0` 或空时，视为未配置该能力（仅当明确允许关闭时才支持该语义；默认值仍为 `10000￥`）

### 4.1.3 数据设计

当前已有：

- `tenant_quota_policies`：请求数 / token 上限策略
- `tenant_quota_usage_periods`：请求数 / token 周期用量
- `tenant_usage_ledger`：租户费用账本

建议一期采用最小改造：

- 在 `tenant_quota_policies` 增加月度金额上限字段，例如：
  - `cost_limit_microyuan bigint not null default 0`

不单独引入新的治理表，避免本期引入第二套配置源。

### 4.1.4 校验设计

金额校验的计算来源建议使用：

- `tenant_usage_ledger`

按自然月窗口聚合：

- `bucket_start >= 当前月开始`
- `bucket_start < 下月开始`

原因：

- `tenant_usage_ledger` 已是租户级聚合账本
- 比直接扫 `llm_request_logs` 成本更低
- 与账单页天然一致

### 4.1.5 前端设计

审批弹窗增加：

- `月度金额上限（￥）`

要求：

- 默认展示 `10000`
- 数值型输入
- 不允许负数
- 提示文案明确“按自然月统计”

## 4.2 租户账单页与关联供应商展示

### 4.2.1 目标

为 admin 提供“按部门/租户查看账单”的能力。

账单页需要回答三个核心问题：

1. 这个部门本月用了多少钱？
2. 这笔钱分别消耗在哪些模型和供应商上？
3. 这个部门主要通过哪些平台 API Key / 业务系统在调用？

### 4.2.2 展示维度

一期建议账单页至少包含：

- 账单周期（自然月）
- 租户 ID / 租户名称
- 总请求数
- 总 Token
- 总费用
- 关联供应商列表
- 供应商分项费用
- 模型分项费用
- 平台 API Key 分项费用

### 4.2.3 “关联供应商”的定义

这里的“关联供应商”不是静态配置的所有 provider，而是：

- 在所选账单周期内，该租户真实发生过调用、并产生过日志/费用的供应商集合

关联依据：

- `llm_request_logs.provider_credential_id`
- join `provider_credentials`
- 再映射为 `provider / display_name`

### 4.2.4 数据来源建议

- 租户汇总：优先来自 `tenant_usage_ledger`
- 供应商 / 模型 / API Key 分项：来自 `llm_request_logs`

原因：

- 汇总走聚合账本，页面响应更稳定
- 分项走明细日志，能够保留真实供应商归因

### 4.2.5 页面建议

左侧或顶部筛选：

- 时间窗口：本月 / 上月 / 自定义月
- 租户

主区域：

1. 概览卡片
   - 总费用
   - 总请求数
   - 总 Token
   - 活跃 API Key 数

2. 供应商费用表
   - 供应商
   - 请求数
   - Token
   - 费用
   - 占比

3. 模型费用表
   - 模型
   - 供应商
   - 请求数
   - 费用

4. API Key 费用表
   - API Key 名称
   - 请求数
   - 费用

## 4.3 输入校验、敏感数据防泄露与脱敏

### 4.3.1 范围收敛

用户提出的需求原文包括：

- 输入校验
- 内容审核
- 敏感数据防泄露
- 正则替换，例如手机号、身份证号中间几位替换为 `XXX`

本期建议只做：

1. **基础输入校验**
2. **敏感数据脱敏**
3. **日志落库前防泄露**

本期不做：

- 复杂内容审核工作流
- 外部审核服务编排
- 可配置审核策略平台
- 多级拦截与人工复核流程

### 4.3.2 一期基础校验

请求进入网关后，至少校验：

- `model` 非空
- `messages` 非空
- 单条 message `role/content` 合法
- `content` 长度上限
- 整体 body 大小上限
- `max_tokens` 合法区间

这些属于输入可靠性，不涉及语义审核。

### 4.3.3 一期脱敏规则

建议先内置一组固定规则，对进入日志、审计或失败记录的用户原文做脱敏：

- 手机号脱敏
- 身份证号脱敏
- 邮箱局部脱敏
- 银行卡号局部脱敏（如果系统里可能出现）

例如：

- `13812345678` -> `138XXX5678`
- `110101199001011234` -> `110101XXXXXX1234`

### 4.3.4 脱敏位置

一期建议的脱敏位置：

1. **日志落库前**
   - `llm_request_logs.error_message`
   - 审计详情
   - playground / 调试场持久化内容

2. **控制台展示前**
   - 再做一次展示态保护，避免历史脏数据直出

### 4.3.5 是否拦截原请求

一期默认：

- **脱敏用于日志与展示，不改写上游真实请求正文**

原因：

- 很多模型任务依赖原始文本语义
- 直接改写正文会改变回答效果
- 脱敏改写更适合日志安全，不适合默认改写业务语义

如果后续需要“转发前也做正文脱敏”，应作为独立安全模式配置。

## 5. 二期设计范围：用户级调用与监控

## 5.1 二期目标

二期目标是让平台从“部门级治理”升级到“员工级治理”。

用户级监控应至少支持：

- 某员工调用次数
- 某员工 Token 消耗
- 某员工金额消耗
- 某员工错误率 / 超时率 / 限流命中
- 某员工使用模型与供应商分布

## 5.2 用户维度定义

二期用户维度确定为：

- **员工工号 `employee_no`**

不复用现有：

- `tenant_id`
- `console_user`
- 平台 API Key 归属 `user_id`

原因：

- `tenant_id` 代表部门，不代表员工
- `console_user` 代表后台操作者，不代表业务调用人
- `platform_api_key` 归属用户只能说明“这个 key 属于谁”，不能代表每次真实使用该 key 的员工

## 5.3 二期能力边界

二期建议实现：

1. 请求链路支持员工工号透传
2. 日志、失败、聚合链路补 `employee_no`
3. 控制台支持按员工过滤和聚合
4. 单员工限流
5. 单员工审计与明细追踪

二期不建议和一期混做的原因：

- 需要新增请求协议维度
- 需要补身份可信性设计
- 需要重新设计限流 key、聚合粒度和账单分摊口径

## 5.4 用户级认证与可信性

二期即便引入 `employee_no`，也不能只靠客户端明文上传就直接信任。

需要至少有一种“可验证来源”机制：

- HMAC 签名（优先）
- 企业 SSO / JWT（后续增强）

否则任何调用方都能伪造别人工号，用户级审计和限流将失去可信性。

## 6. TODO / 后续阶段评估

## 6.1 多 key 轮询与负载均衡

复杂度：**中高**

原因：

- 需要一个模型挂多个 provider credential
- 需要路由选择策略、健康权重、失败剔除、费用归因
- 会与后续熔断和主备切换强耦合

建议：放二期后或三期。

## 6.2 语义缓存

复杂度：**高**

原因：

- 需要 embedding 或相似度索引
- 需要缓存命中阈值、失效策略、缓存污染控制
- 需要严格租户隔离，避免跨部门命中

建议：放 TODO，不进入当前主线。

## 6.3 MCP 协议打通

复杂度：**研究项，不是本期主线**

原因：

- 这是产品边界和生态接入问题
- 不直接影响一期的治理、账单与安全能力闭环

建议：仅做研究评估，不纳入本期开发。

## 6.4 单一用户请求限流

复杂度：**中**，但前提是用户维度先落地

由于一期不引入 `employee_no`，当前没有真实的业务终端用户维度，因此本项推迟到二期更合理。

## 6.5 自动熔断与错误率降级

复杂度：**中高**

原因：

- 当前已有健康检查，但没有“错误率滑窗 -> 自动熔断 24h -> 路由侧避让 -> 自动恢复”的全闭环
- 需要补状态机和统计窗口逻辑

建议：二期或三期。

## 6.6 TTFT 超时切换备用模型

复杂度：**高**

原因：

- 要处理流式首字延迟超时
- 要主动取消上游连接
- 要切主备并重新组织响应
- 要解决幂等、重试、回退与用户体验一致性问题

建议：三期后做。

按优先级建议：

1. 租户自然月金额上限
2. 租户账单页与关联供应商展示
3. 基础输入校验 + 脱敏

### 7.2 二期优先级

4. 语义缓存
5. MCP 研究与接入

## 8. 业务价值

### 8.1 一期价值

在企业内部场景中，一期能力可以直接作为：

- **部门级 AI 成本治理平台**
- **部门级 AI 账单与对账平台**
- **企业内部 AI 输入安全基线能力**

它能解决：

- 哪个部门花了多少钱
- 钱花在了哪些供应商和模型上
- 哪些输入可能带来敏感信息泄露风险
- 部门额度是否可控

### 8.2 二期价值

二期能力可以进一步作为：

- **员工级 AI 使用监控平台**
- **员工级 AI 风险审计平台**
- **员工级 AI 使用治理平台**

它能解决：

- 哪个员工在高频使用 AI
- 哪个员工费用异常高
- 哪个员工频繁命中错误、超时或风控
- 哪些使用行为需要进一步治理

## 9. 风险与边界说明

1. 一期如果把“内容审核”和“脱敏”混为一体，会导致范围过大，必须拆开处理。
2. 二期如果没有可信身份设计，仅引入 `employee_no` 字段会导致伪造风险。
3. 多 key、熔断、主备切换属于路由控制平面升级，不应混入本期账单与治理改造。
4. 若后续需要财务口径对接，账单页还应支持导出与结算状态管理，但这不属于一期必须项。

## 10. 最终建议

当前最合理的路线是：

- **一期先做部门级治理**：金额上限、账单、输入安全
- **二期再做员工级治理**：用户级调用、监控、限流、审计
- **更重的高可用路由能力放后续**：熔断、TTFT 切备、多 key、语义缓存

这样既能保证本期改造落地速度，也不会把未来用户级治理和高可用路由的演进空间锁死。

## 11. 一期详细实现清单

本节把一期范围进一步拆成可执行的实现任务，供后续直接转 implementation plan。

### 11.1 一期范围定义

一期只实现以下三块：

1. **审批增加租户自然月金额上限**
2. **租户账单页与关联供应商展示**
3. **基础输入校验与敏感信息脱敏**

不在一期范围内：

- 用户级维度
- 熔断与降级自动化
- TTFT 切备
- 多 key
- 语义缓存

### 11.2 后端改造清单

#### 11.2.1 审批与租户策略

目标：审批时把“月度金额上限”落到租户策略中，并在请求入口进行金额校验。

建议改动：

1. 扩展审批请求结构
   - 在 admin 审批接口 payload 中增加金额上限字段
   - 单位建议前端按“元”输入，后端统一转成 `microyuan`

2. 扩展租户策略存储
   - 在 `tenant_quota_policies` 增加 `cost_limit_microyuan`
   - 审批通过时同步写入该字段

3. 扩展租户额度校验器
   - 现有 `QuotaGuard` 主要处理请求数 / token 额度
   - 一期建议在同一治理入口增加“金额额度校验”
   - 不要单独做第二套入口，避免拦截点分裂

4. 新增金额超限错误语义
   - 仍可沿用统一“quota exceeded”错误码
   - 但内部错误分类、日志和前端文案需要能区分：
     - 请求数超限
     - Token 超限
     - 金额超限

#### 11.2.2 账单查询接口

目标：让 admin 后台能够按租户查看自然月账单。

建议新增或扩展接口：

1. 账单概览接口
   - 输入：`tenant_id`、`month`
   - 输出：总费用、总请求数、总 Token、活跃 API Key 数

2. 供应商账单分项接口
   - 输入：`tenant_id`、`month`
   - 输出：供应商、请求数、Token、费用、占比

3. 模型账单分项接口
   - 输入：`tenant_id`、`month`
   - 输出：模型、供应商、请求数、费用

4. API Key 账单分项接口
   - 输入：`tenant_id`、`month`
   - 输出：API Key、请求数、费用

如果想控制接口数量，也可以合并成一个：

- `GET /api/admin/billing/tenant?tenant_id=...&month=2026-05`

返回：

- `summary`
- `providers`
- `models`
- `api_keys`

一期更推荐单接口聚合返回，前端接入更快。

#### 11.2.3 输入校验与脱敏

目标：先把“安全基线”补齐，而不是做重型内容审核系统。

建议改动：

1. 聊天入口基础校验
   - 校验 `model`
   - 校验 `messages`
   - 校验 `messages[].role/content`
   - 限制 content 长度
   - 限制 body 大小
   - 校验 `max_tokens` 合法范围

2. 向量入口基础校验
   - 校验 `model`
   - 校验 `input`
   - 限制输入长度与数量

3. 新增通用脱敏函数
   - 手机号
   - 身份证号
   - 邮箱局部脱敏
   - 预留银行卡号规则扩展点

4. 在日志落库前调用脱敏
   - `llm_request_logs.error_message`
   - 审计详情
   - playground 持久化内容
   - 失败原因摘要

5. 在控制台展示侧做二次保护
   - 即使历史旧数据未脱敏，页面展示也先经过安全转换

### 11.5 运行时行为清单

#### 11.5.1 请求前检查顺序建议

聊天 / 向量请求进入网关后的顺序建议统一为：

1. 认证平台 API Key
2. 解析 `tenant_id`
3. 校验租户状态
4. 校验租户请求数 / token 配额
5. 校验租户自然月金额上限
6. 校验模型是否允许
7. 校验请求体合法性
8. 记录请求上下文
9. 转发上游
10. 记录日志与费用

这样可以保证：

- 超限请求不会打上游
- 非法请求不会污染上游调用日志
- 金额治理与现有治理链路保持一致

#### 11.5.2 脱敏生效位置

脱敏建议不改写真正转发给上游的请求正文，只影响：

- 落库内容
- 控制台展示内容
- 错误日志/审计详情

## 13. 文档使用建议

后续如果继续实施，建议顺序为：

1. 基于本设计文档写一期 implementation plan
2. 先落“金额上限”闭环
3. 再落“账单页”
4. 最后落“输入校验与脱敏”

原因：

- 金额上限最直接体现治理价值
- 账单页最直接体现业务可见性
- 输入校验与脱敏更适合作为收尾安全基线能力纳入
