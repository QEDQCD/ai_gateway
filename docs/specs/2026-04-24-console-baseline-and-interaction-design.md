# AI Gateway 控制台入口语义与交互闭环基线设计

## 1. 背景

当前控制台存在以下产品与实现问题：

- 左侧 `控制台预览版 / 启动模式 / 网关健康` 仅为静态文案，点击无行为，容易误导用户。
- 用户会把 `31873`、`32658`、`31427` 都理解成“可登录后台”，但它们的真实语义并不一致。
- 前端暴露了 `知识库` / `RAG` 感知入口，但本轮并不准备完整实现 RAG 产品闭环。
- `API 密钥` 页面存在 `新建密钥 / 轮换密钥 / 停用密钥` 按钮，但没有真实前后端联动。
- 其他页面中存在“可见但不真实”的操作或状态入口，破坏产品可信度。

本设计用于定义一轮“控制台基线修复”，目标不是做大规模重构，而是让当前控制台满足两个最低标准：

1. 用户能清楚理解唯一正式入口、内部接口和状态信息的边界。
2. 页面上凡是展示出来的交互，必须真实可用。

## 2. 目标

本轮目标：

- 明确 `31873` 是唯一正式控制台入口。
- 明确 `32658` 是网关管理 API，而不是第二套后台。
- 明确 `31427` 是内部服务端口，前端不再暴露其产品入口。
- 隐藏前端中的 RAG / 知识库产品感知。
- 把左侧状态区改造成有语义的真实状态入口。
- 补齐 `API 密钥` 生命周期管理的前后端闭环。
- 审计当前控制台所有已暴露的可点击项，确保“显示出来就能真实联动”。

## 3. 非目标

本轮明确不做：

- 不实现完整 RAG 产品能力闭环，不做上传文档、切片管理、检索生成可视化后台。
- 不新增第二套后台，不做 `32658` 专属网页后台。
- 不做调用观测与路由页的大规模可视化升级。
- 不重构整个控制台技术栈，不引入新的登录体系或权限体系。
- 不做审核流、多角色审批流、复杂租户治理流。

## 4. 已确认约束

基于本轮沟通，约束固定如下：

- `RAG` 整体在前端先隐藏，暂不实现用户可见产品能力。
- 控制台唯一正式入口为 `31873`。
- `32658` 为管理 API。
- `31427` 为内部服务。
- 左侧状态区采用“保留但可点击”的方案，而不是删除或保留静态展示。
- 页面上凡是展示出来的操作，都必须真实联动。
- `API 密钥` 的 `新建 / 轮换 / 停用` 需做到：
  - 真实写库
  - 真实立即生效
  - 二次确认（危险操作）
  - 成功反馈
  - 失败反馈
  - 列表刷新

## 5. 产品边界与入口语义

### 5.1 入口定义

- `http://<host>:31873`
  - 唯一正式控制台入口
  - 用户访问后台只通过此入口
- `http://<host>:32658`
  - 网关管理 API 与健康检查端口
  - 不承担“后台登录页”语义
- `http://<host>:31427`
  - 内部 RAG 服务端口
  - 不在前端出现入口，不在控制台中暗示其为单独后台

### 5.2 页面与文案要求

- 控制台内不再出现任何“RAG 管理台”“知识库后台”“第二后台入口”等暗示性文案。
- 涉及运行模式、系统状态、端口说明的文案，必须明确区分：
  - 可视化控制台
  - 管理 API
  - 内部服务

## 6. 信息架构调整

### 6.1 保留页面

- 总览
- API 密钥
- 路由
- 调试场
- 调用观测
- 审计

### 6.2 隐藏页面

- 知识库

要求：

- 左侧导航移除 `知识库`
- 路由定义中不再将 `知识库` 作为对外可达导航项
- 若出于兼容性保留内部路由，前端不得暴露入口

## 7. 左侧状态区设计

当前左侧状态区的三个 badge：

- 控制台预览版
- 启动模式
- 网关健康

本轮统一改为“状态入口项”，具体如下。

### 7.1 控制台预览版

点击后打开一个说明弹层或右侧抽屉，展示：

- 当前版本定位：控制台预览版
- 本轮已开放功能
- 本轮未开放功能
- 明确说明：
  - RAG 产品后台未开放
  - `32658` 和 `31427` 不是后台入口

### 7.2 启动模式

点击后打开“部署与运行模式”弹层，展示真实运行信息：

- 当前模式：数据库模式 / 启动模式说明
- 正式控制台入口：`31873`
- 管理 API：`32658`
- 内部服务：`31427`
- 认证方式说明：
  - 控制台 / 管理 API 使用 Basic Auth
  - 平台调用使用 Bearer API Key

该信息必须来自真实后端接口，而不是前端硬编码拼装。

### 7.3 网关健康

点击后跳转到有实际数据支撑的区域，优先方案：

- 跳转到总览页中的健康区块

备选方案：

- 跳转到调用观测页并默认显示最近时间窗口

本轮不要求新建专门健康大盘页，但必须有真实跳转与真实数据来源。

## 8. 顶部状态区设计

顶部 `网关健康 / 配额保护已启用` 两个 badge 也必须具备语义：

- `网关健康`
  - 点击行为与左侧一致，跳到真实健康信息
- `配额保护已启用`
  - 点击后展示当前限流/配额机制说明
  - 可与“启动模式”弹层复用一部分系统状态数据

如果不能真实联动，则本轮应降级为纯文本，不渲染成可点击状态。

## 9. API 密钥生命周期设计

### 9.1 页面目标

`API 密钥` 页从静态展示页升级为最小可用管理页，支持：

- 查看列表
- 选中某条 key
- 创建新 key
- 轮换已有 key
- 停用已有 key

### 9.2 列表交互

列表需支持单选当前 key。

每条记录至少包含：

- `id`
- `name`
- `tenant`
- `status`
- `scopes`
- `last_used_at`

前端根据当前选中项状态控制按钮可用性：

- `新建密钥`
  - 始终可用
- `轮换密钥`
  - 仅当已选中一条可轮换 key 时可用
- `停用密钥`
  - 仅当已选中一条 active key 时可用

### 9.3 新建密钥

前端：

- 点击 `新建密钥`
- 打开弹窗
- 字段：
  - 名称
  - 租户
  - 权限范围
- 提交后显示 loading

后端：

- 创建平台 API Key 记录
- 持久化 hash 与元数据
- 返回一次性明文 key

前端成功反馈：

- 弹窗显示“只展示一次”的明文 key
- 要求用户立即保存
- 关闭弹窗后不再回显
- 刷新列表

### 9.4 轮换密钥

前端：

- 需要先选中一条 key
- 点击 `轮换密钥`
- 显示确认弹窗，明确提示旧 key 将失效

后端：

- 生成新的原始 key
- 更新存储中的 hash
- 刷新最近更新时间或轮换时间
- 保持 key 逻辑身份不变，或明确记录轮换后版本

前端成功反馈：

- 返回一次性新 key
- 刷新列表
- 显示成功提示

### 9.5 停用密钥

前端：

- 需要先选中一条 active key
- 点击 `停用密钥`
- 显示危险确认框

后端：

- 将状态改为 `inactive` / `disabled`

前端成功反馈：

- 刷新列表
- 按钮状态立即更新

### 9.6 安全规则

- 列表接口永不返回明文 key
- 创建和轮换接口只在成功时返回一次明文 key
- 失败时不得返回部分敏感数据
- 继续复用现有 Basic Auth 作为管理操作认证

## 10. 前后端接口设计

### 10.1 系统状态接口

新增建议接口：

- `GET /api/admin/system/status`

返回建议字段：

- `console_entry`
- `gateway_admin_api`
- `internal_services`
- `run_mode`
- `gateway_health`
- `quota_protection`
- `console_stage`
- `hidden_modules`

用途：

- 左侧状态区
- 顶部状态区
- “控制台预览版 / 启动模式”说明弹层

### 10.2 API 密钥管理接口

新增建议接口：

- `POST /api/admin/api-keys`
- `POST /api/admin/api-keys/:id/rotate`
- `POST /api/admin/api-keys/:id/deactivate`

保留已有：

- `GET /api/admin/api-keys`

### 10.3 错误码规则

所有管理动作统一遵循：

- `400` 参数错误
- `401` 未认证
- `404` 对象不存在
- `409` 状态冲突或不可执行
- `500` 服务内部错误

前端不得把所有失败都展示成同一条模糊错误。

## 11. 页面级联动基线

### 11.1 总览页

本轮要求：

- 健康区块真实显示
- 点击健康状态后能跳转或定位到真实内容
- 运行模式信息不得再是纯静态装饰

### 11.2 API 密钥页

本轮要求：

- 新建、轮换、停用 3 个动作全部真实可用
- 所有操作完成后刷新列表
- 列表选中状态与按钮禁用逻辑一致

### 11.3 路由页

本轮要求：

- 保持只读也可以
- 但如果页面里展示为可点击操作，则必须联动
- 路由健康状态若对用户展示，应绑定真实后端数据

### 11.4 调试场

本轮要求：

- 保留真实模型请求调用能力
- 最近一次结果与执行元数据保持同步
- 不出现加载完成后短暂空白或伪状态

### 11.5 调用观测

本轮要求：

- 保持现有已打通接口
- 保持筛选、翻页、错误优先逻辑正常
- 暂不做新的大可视化改版

### 11.6 审计

本轮要求：

- 只展示真实已实现内容
- 不新增假按钮

## 12. 数据与存储设计

### 12.1 API Key 数据

需支持以下字段或等价字段：

- `id`
- `tenant_id`
- `name`
- `status`
- `scopes`
- `key_hash`
- `last_used_at`
- `updated_at`

如当前表结构不足，需要新增迁移。

### 12.2 轮换逻辑

轮换不应创建一个“完全脱离原身份的新业务对象”而导致前端列表混乱。

推荐做法：

- 保持同一 `id`
- 更新 hash 与时间戳
- 返回新的原始 key 一次

若现有存储模型不支持，也可采用“旧 key 停用 + 新 key 创建”的实现，但前端与接口必须明确表达这一点。

## 13. 前端实现约束

- 不允许保留“能点但没行为”的按钮
- 不允许再暴露 `知识库` / RAG 导航入口
- 所有弹层与确认框必须是中文
- 所有状态说明必须用真实接口驱动，不允许前端纯硬编码伪装成系统状态
- 页面上危险操作必须有确认

## 14. 测试设计

### 14.1 前端测试

至少覆盖：

- 左侧状态项点击行为
- `知识库` 导航隐藏
- `API 密钥` 的新建、轮换、停用成功路径
- `API 密钥` 的失败提示路径
- 按钮禁用逻辑
- `调试场` 不回归
- `调用观测` 不回归

### 14.2 后端测试

至少覆盖：

- `GET /api/admin/system/status`
- `POST /api/admin/api-keys`
- `POST /api/admin/api-keys/:id/rotate`
- `POST /api/admin/api-keys/:id/deactivate`
- 明文 key 只返回一次
- 非法状态操作返回正确错误码
- 未授权访问被拒绝

### 14.3 联调验证

部署后需手工验证：

- `31873` 是唯一正式控制台入口
- 控制台里不再出现 `知识库`
- 左侧 3 个状态项可点且有真实反馈
- `32658` 作为 API 使用正常，但不被当成后台入口
- `31427` 前端无入口
- `API 密钥` 三个动作可完整走通

## 15. 验收标准

本轮完成后，必须满足：

- 用户进入控制台时不会再混淆三个端口的角色。
- 控制台中不再暴露尚未准备好的 RAG 产品能力。
- 左侧状态区从“无意义装饰”变成“有语义的状态入口”。
- `API 密钥` 页面从静态页变成可管理页。
- 当前控制台中所有可见操作都具备真实联动。

## 16. 实施顺序建议

建议实现顺序：

1. 新增系统状态接口
2. 前端导航与状态区改造
3. 隐藏 `知识库` / RAG 前端入口
4. 补齐 API Key 管理后端接口
5. 补齐 API Key 前端交互与联调
6. 全量审计其他可见交互，清掉假按钮
7. 联调与部署验证

## 17. 风险与注意事项

- 当前工作区已存在较多控制台和后端改动，实现时必须避免覆盖已有功能。
- API Key 的“明文只展示一次”如果处理不当，容易留下泄露风险。
- 隐藏 RAG 前端入口时，要注意不要误伤网关后端内部对 RAG 的真实代理调用。
- 左侧状态区如果继续使用纯静态文案，会再次造成“可点击但无意义”的产品回归，因此必须由真实接口驱动。
