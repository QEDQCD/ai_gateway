# Admin 租户管理与账单合并设计

## 背景

当前 admin 控制台中：

- `租户管理` 页面负责展示租户治理总览、密钥聚合、平台调用概况
- `账单` 页面负责按 `tenant + month` 查看单租户月度账单明细

这两个页面都围绕“租户”展开，且都包含调用量、费用、密钥等信息。当前拆成两个左侧一级页面，存在明显冗余：

1. 用户先在 `租户管理` 找到租户，再切到 `账单` 输入租户 ID，路径重复。
2. 两个页面都承载租户视角的数据，但上下文断裂，操作不连续。
3. `账单` 页面只有在知道租户 ID 后才有意义，不适合继续作为独立一级导航。

## 目标

- 将 `账单` 页面彻底并入 `/tenants`。
- 左侧移除 `账单` 一级导航，只保留 `租户管理`。
- 在 `租户管理` 页面内直接查看指定租户的自然月账单详情。
- 保留现有账单数据结构与后端接口能力，优先做前端信息架构合并。
- 降低 admin 在“租户治理”和“费用分析”之间切换的成本。

## 非目标

- 不新增新的账单计算逻辑。
- 不改造账单后端接口协议。
- 不做多租户并排对比账单。
- 不做导出、打印、下载等二期能力。
- 不保留 `/billing` 兼容路由。

## 已确认决策

- `账单` 不再作为独立一级页面存在。
- 账单能力彻底并入 `/tenants`。
- 在 `/tenants` 中采用 **列表 + 同页详情区** 的交互模式。
- 账单详情按“当前选中的单个租户 + 指定自然月”展示。

## 方案对比

### 方案 A：列表 + 同页详情区

做法：

- `/tenants` 继续展示租户治理列表。
- 每个租户行增加 `查看账单` 操作。
- 点击后在同页下方展示该租户的月账单详情区。

优点：

- 治理与费用放在同一上下文中，路径最短。
- 用户先看“租户是谁”，再看“这个租户花了多少”，认知连续。
- 不需要额外的弹窗或路由跳转。

缺点：

- 页面长度会增加。

### 方案 B：列表 + 弹窗/抽屉

做法：

- 点击租户行操作后，用弹窗或右侧抽屉展示账单详情。

优点：

- 页面主结构稳定。

问题：

- 账单内容本身较长，包含概览、Provider、模型、API Key 四段，放在弹窗/抽屉中可读性一般。
- 后续筛月份、切换租户时交互会更重。

### 方案 C：切换 Tab

做法：

- `/tenants` 页面顶部提供 `租户概览 / 租户账单` 两个 Tab。

优点：

- 页面层次清晰。

问题：

- 仍然需要先选择租户，再切换账单视图，本质上还是分屏而非真正合并。
- 对“从某个租户直接下钻看账单”的支持不够顺手。

## 结论

采用 **方案 A：列表 + 同页详情区**。

原因：

- 这是最符合“彻底并入 `/tenants`”的实现方式。
- 账单本身是租户治理的下钻视图，不应继续成为并列一级页面。

## 信息架构设计

### 左侧导航

admin 左侧导航调整为：

1. `总览`
2. `账号申请`
3. `租户管理`
4. `API 密钥`
5. `调用观测`
6. `审计`
7. `后台模型`
8. `健康检查`

变化点：

- 移除 `账单`

### `/tenants` 页面结构

页面分为三层：

1. **租户治理概览**
   - 保留现有租户数、启用密钥、总调用数、成功率、总费用等卡片
2. **租户治理列表**
   - 保留当前租户聚合表格
   - 每行新增 `查看账单` 操作
3. **租户账单详情区**
   - 位于页面下方
   - 默认空态
   - 选中租户后加载账单明细

## 交互设计

### 默认态

- 页面初次进入时，只显示租户治理概览和租户治理列表
- 账单详情区显示空态提示，例如：
  - `请选择一个租户查看自然月账单`

### 查看账单

- 用户在租户行点击 `查看账单`
- 页面内记录当前选中租户
- 页面滚动或聚焦到账单详情区
- 默认月份为当前自然月
- 拉取该租户该月份的账单详情

### 切换月份

- 账单详情区顶部保留月份筛选
- 用户切换月份后，仅刷新账单详情区
- 不影响上方租户治理列表

### 切换租户

- 点击另一个租户的 `查看账单`
- 替换当前选中租户
- 保留当前月份，或若未选过则默认当前月

建议行为：

- 若用户已主动改过月份，则切换租户时沿用该月份
- 这样方便做“同月份跨租户查看”

## 页面内容设计

### 租户治理列表

在现有列基础上新增一列：

- `操作`

操作内容：

- `查看账单`

### 账单详情区

继续保留现有账单页的四段结构：

1. **账单概览**
   - 请求数
   - 成功/失败
   - 总 Token
   - 总费用
   - 输入/输出/缓存 Token 与费用
2. **Provider 分项**
3. **模型分项**
4. **API Key 分项**

顶部增加当前上下文信息：

- 当前租户 ID
- 当前月份

## 路由设计

### 保留

- `/tenants`

### 删除

- `/billing`
- `adminNavigation` 中对应账单导航项

### 查询参数

建议让 `/tenants` 支持可选查询参数：

- `tenant`
- `month`

用途：

- 允许页面刷新后保留账单详情上下文
- 允许未来从其他页面直接深链到某个租户的某月账单详情

示例：

- `/tenants?tenant=tenant_demo&month=2026-05`

虽然账单已并入 `/tenants`，但保留查询参数有利于状态恢复。

## 数据与实现边界

### 前端

- `AdminTenantsPage` 承担合并后的容器职责
- 复用现有 `getTenantBilling(tenantID, month)` 接口
- 复用现有账单页的数据展示结构

### 后端

- 无需新增接口
- 无需调整当前账单聚合逻辑

## 测试设计

至少覆盖以下场景：

### 路由 / 导航

- admin 左侧导航中不再显示 `账单`
- `/tenants` 仍可访问
- `/billing` 不再作为有效入口

### 页面行为

- `/tenants` 页面可展示 `查看账单` 操作
- 点击 `查看账单` 后，会请求对应租户和月份的账单接口
- 默认空态下不请求账单接口
- 切换月份后，会重新请求账单接口

### 状态保持

- `/tenants?tenant=...&month=...` 进入时，直接展示对应账单详情

## 风险与控制

### 风险 1：页面职责变重

控制：

- 维持清晰的三段布局：概览、列表、详情
- 不把账单字段直接塞进租户列表

### 风险 2：`AdminTenantsPage` 文件继续膨胀

控制：

- 允许提取账单详情子组件
- 允许提取租户表格行操作逻辑

### 风险 3：状态与 URL 不一致

控制：

- 统一以 `/tenants` 查询参数作为账单详情上下文来源
- 页面内交互同步更新 URL

- 左侧导航不再显示 `账单`。
- `/tenants` 页面可直接从租户列表进入单租户月账单详情。
- 账单详情默认在同页下方展示，而不是跳转到独立页面。
